# 实现 CLI-Anything 式能力（移动端）— 工期估算与难点

> 范围：在移动端实现「从 UI/契约自动生成结构化、可发现、可执行接口」的 CLI-Anything 式能力，供 Agent 使用。  
> 假设：基于现有 phone_pilot（MCP + get_page_state + tap_element + open_deeplink 等），Android 优先。

---

## 1. 范围界定

**要实现的“功能”对齐 CLI-Anything 的核心理念**：

| CLI-Anything（桌面） | 移动端对应目标 |
|----------------------|----------------|
| 对目标软件一键生成「该软件的 CLI」 | 对目标 App 一键（或半自动）生成「该 App 的页面 + 可执行操作」描述与调用接口 |
| 输入：软件源码 | 输入：UI 树 + 可选 deeplink/契约 |
| 产出：Click CLI 包（--help / --json） | 产出：页面 ID + 操作列表 schema，以及 Agent 可调用的执行层（现有 MCP 或封装） |
| Agent 通过 CLI 发现能力并组合执行 | Agent 通过 schema/工具发现「当前页能做什么」并组合执行 |

**不包含**：复刻 CLI-Anything 的 7 阶段流水线到移动端；仅实现「分析 → 设计 → 实现」中与移动端适配的核心链路，并产出可被 Agent 使用的结构化描述与执行能力。

### 1.1 一期范围：仅在自己的有源码 App 上跑通

- **约束**：一开始只要求在你**拥有源码的这一个 App** 上跑通整条链路即可，不要求支持任意第三方 App。
- **含义**：
  - 目标 App 唯一、可控，可针对其做定制（如固定 package、固定 deeplink 列表、已知 Activity 列表）。
  - 有源码即可做**静态分析**（见下），页面列表与 deeplink 可从源码得出，无需通用「无源码探索器」。
- **工期与难点**：在此范围内，页面发现与遍历难度显著下降，工期可取下述「一期（自有源码 App）」估算。

### 1.2 有源码时的差异与优势

| 维度 | 无源码（通用） | 有源码（一期：你的 App） |
|------|----------------|---------------------------|
| **页面/入口发现** | 只能运行时遍历或人工维护列表 | 可从源码**静态扫**：AndroidManifest（Activity、intent-filter）、deeplink/scheme 声明、路由配置等，得到 Activity 列表与 deeplink 列表 |
| **页面列表** | 需探索或契约 | **从源码生成**：Activity → 页面 ID 候选；intent-filter / URI 即 deeplink 清单 |
| **遍历策略** | 需通用探索器（点击、去重、弹窗） | 只需按「源码得出的 deeplink + Activity 列表」**逐页打开**，用现有 `phone_open_deeplink` + `phone_get_page_state` 即可 |
| **定制与调试** | 难以针对单 App 优化 | 可针对该 App 的包名、启动 Activity、权限与弹窗做专门处理 |
| **回归** | 无源码则只能运行时校验 | 源码变更（如新增 Activity、改 deeplink）可驱动「重新生成 schema」或 CI 检查 |

**技术可选**：对 Android 源码可做轻量静态分析，例如解析 `AndroidManifest.xml`（APK 解包或从源码工程读取）、扫描 `intent-filter` 与 `data/android:scheme` 得到 deeplink 列表；若有路由库（如 ARouter、DeepLink 注解），可扫注解得到「path → Activity」映射。这样**无需**先跑 App 就能得到「要覆盖的页面/deeplink 清单」，再在真机/模拟器上逐页打开并跑单页解析即可。

## 2. 工期估算（人天 / 人月）

假设 **1 人全职、熟悉现有 phone_pilot 与 Android 自动化**，按阶段粗估如下。

| 阶段 | 内容 | 人天（粗估） | 说明 |
|------|------|--------------|------|
| **1. Schema 与数据模型** | 定义「页面 ID + 可执行操作列表」的 JSON Schema / 数据模型；与 `phone_get_page_state` 输出对齐；设计「发现接口」（类似 --help/--json） | 5～10 | 可复用《页面结构化描述与自动化脚本方案》中的设计 |
| **2. 单页解析** | 从一次 `get_page_state` 的 raw 结果生成「当前页的页面 ID + 操作列表」；含可点击/可输入/可滑动、deeplink 的识别与归一化 | 10～15 | 依赖现有 dump_ui、elements 过滤逻辑；难点在语义化与稳定性 |
| **3. 页面发现与遍历** | 在「自己 App」内做页面发现：通过 deeplink 列表 + 或基于现有操作的自动探索（点击可点元素进入新页），收集多页并去重（同一 Activity 不同参数算一页还是多页需约定） | 15～25 | **难点集中**：探索策略、去重、弹窗/返回处理 |
| **4. 整 App 描述生成** | 把「多页 + 每页操作列表」汇总为一份「App 能力描述」（单文件或分页文件）；支持导出为 JSON/YAML，供 Agent 或后续脚本读取 | 5～10 | 与阶段 1 的 schema 一致即可 |
| **5. Agent 侧发现与执行** | 让 Agent 能「发现」该描述：例如新增 MCP 工具 `phone_get_app_capabilities(package)` 返回 schema，或把描述注入到 Agent 的 system/context；执行仍用现有 `phone_tap_element`、`phone_open_deeplink` 等 | 5～10 | 若仅读文件并注入，工作量小；若做成动态 MCP 需更多设计 |
| **6. 流水线入口与文档** | 一条命令或一个脚本：对指定 package（+ 可选 deeplink 列表）跑「遍历 → 单页解析 → 汇总 → 输出 schema」；README 与使用说明 | 5～8 | 串联现有能力为主 |
| **7. 测试与边界** | 在 1～2 个 Demo App 上验证；处理权限/弹窗/首次启动/深层级页面；简单回归（改版后重新生成并 diff） | 10～15 | 易被低估，建议预留 |

**合计（单人不含项目管理与联调缓冲）**：约 **55～93 人天**，折合 **约 2.5～4.5 人月**。

**一期：仅在自己的有源码 App 上跑通**（推荐优先采用）：

- 页面列表与 deeplink 从**源码静态分析**得出，无需通用探索器；遍历简化为「按清单逐页 open_deeplink + get_page_state + 单页解析」。
- 阶段 3「页面发现与遍历」可收缩为：**从源码扫 Activity / deeplink → 生成待覆盖列表 → 脚本逐页打开并解析**，约 **5～10 人天**（替代原 15～25）。
- 阶段 7 测试仅针对这一款 App，可收敛到 **5～8 人天**。
- **一期合计**：约 **40～58 人天**，折合 **约 2～2.5 人月**；若再砍掉「多 App 泛化」相关设计，可压到 **约 1.5～2 人月**。

若只做 **MVP**（单页解析 + 手动维护页面列表 + 生成单 App 的 schema + Agent 可读）：可压缩到 **约 1～1.5 人月**。  
若要做 **全自动探索 + 多 App 泛化 + 与脚本生成/自愈联动**：建议按 **3～4.5 人月** 规划，并预留 20%～30% 缓冲。

## 3. 难点分析

### 3.1 输入侧：没有「源码」时只有 UI 树与契约；有源码则可用静态分析

- **问题**：CLI-Anything 的输入是完整源码，可静态分析出能力；移动端**若拿不到 App 源码**，只能依赖 **运行时 UI 树**（dump hierarchy）或 **人工/半人工契约**（deeplink 列表、页面清单）。
- **影响**：无源码时无法「一次性扫完所有能力」，必须通过 **遍历 + 实际进入每一屏** 才能拿到该页的「可执行操作列表」；漏页、重复页、动态页都会增加复杂度和工期。
- **缓解（无源码）**：优先支持「deeplink + 有限页面」的契约驱动；全自动探索作为二期；对「自己 App」可人工维护一份页面/deeplink 白名单。
- **一期（有源码）**：你**有目标 App 的源码**时，可直接从源码做**静态分析**（AndroidManifest、intent-filter、路由注解等）得到 **Activity 列表与 deeplink 列表**，无需通用探索器；只需按该清单逐页打开并做单页解析，此难点在一期范围内**大幅减弱**。

### 3.2 页面 ID 的稳定性与唯一性

- **问题**：同一业务页可能对应不同 Activity（如兼容、AB 实验）；同一 Activity 不同参数（如 `detail?id=1` / `id=2`）算一页还是多页；不同机型/主题/语言下 activity 或资源 id 可能变化。
- **影响**：若页面 ID 设计不当，生成的 schema 在 App 改版或换机后大量失效，维护成本高。
- **缓解**：页面 ID 采用「语义 ID + activity/uri 兜底」；在「自己 App」内约定语义 ID 与 deeplink/Activity 的映射表，由配置或人工维护；自动生成时只填 activity/uri，语义 ID 可选后填。

### 3.3 可操作元素的语义化与稳定性

- **问题**：UI 树只有 index、text、resource-id、class；要变成「提交」「返回」「去设置」等语义，需要 **启发式规则或 LLM**；且 index 会随 UI 变化而变，同一按钮在不同版本可能 index 不同。
- **影响**：生成的「操作列表」若只存 index，改版易断；若要做语义化，需要额外规则或模型，并处理多语言/多主题。
- **缓解**：优先用 **resource-id / content-desc / 稳定 text** 作为操作标识，index 仅作执行时的一次性定位；语义 label 先做「可选」，MVP 阶段可用 text 或 id 代替；后续再引入简单规则或 LLM 归一化语义。

### 3.4 页面发现与遍历策略

- **问题**：要生成「整 App 能力描述」必须覆盖主要页面；**无源码时**自动遍历需要「从首页/deeplink 出发 → 点击可点元素 → 判断是否新页 → 去重 → 递归/队列」，并处理返回、弹窗、登录态、权限弹窗等。
- **影响**：无源码时探索逻辑复杂、易陷入死循环或漏页；不同 App 的导航结构差异大，通用探索器难以做到高覆盖。
- **缓解（无源码）**：一期只做「契约驱动」：人工或配置提供 deeplink 列表 + 可选页面列表，只对已知页做单页解析与汇总；二期再做「有限探索」。
- **一期（有源码）**：页面与 deeplink 清单**从源码静态得出**，遍历只需「按清单逐页 open_deeplink（或 launch Activity）→ get_page_state → 单页解析」，无需通用探索与复杂去重，此难点在一期**显著降低**。

### 3.5 与现有 MCP 的集成方式

- **问题**：生成物是「schema 文件」还是「动态 MCP 工具」？若只产出 JSON，Agent 需要先「读取该 App 的 schema」再决定调用哪些现有 MCP（tap_element、open_deeplink）；若为每个 App 生成一套 MCP 工具，则工具数量膨胀、维护成本高。
- **影响**：设计不当会导致 Agent 侧使用复杂或生成物难以复用。
- **缓解**：MVP 采用「生成 schema 文件 + 1 个通用 MCP 工具（如 phone_get_app_capabilities）返回当前 App 的页面/操作描述」；执行统一走现有 phone_tap_element、phone_open_deeplink 等，不按 App 拆工具。

### 3.6 测试与回归

- **问题**：App 升级、UI 改版后，之前生成的 schema 可能部分失效（元素 index/文本变更、页面合并或拆分）；需要能「重新生成并 diff」或「按页校验」的机制。
- **影响**：若没有回归策略，生成物会逐渐失效，信任度下降。
- **缓解**：提供「按 package 重新生成」的命令；可选「生成前后 diff」或「单页校验脚本」；在 CI 中定期对关键 App 重跑生成并检查关键页面是否仍可定位。

### 3.7 难点优先级（对工期与风险的影响）

| 难点 | 对工期/风险影响 | 建议 | 一期（有源码单 App） |
|------|------------------|------|------------------------|
| 没有源码、只能 UI 树/契约 | 高：决定整体架构与探索上限 | 明确一期契约驱动，探索做二期 | **弱化**：用源码静态分析得到清单 |
| 页面 ID 稳定性 | 中高：影响长期可维护性 | 语义 ID + 映射表，先在自己 App 验证 | 单 App 可定制映射，风险可控 |
| 可操作元素语义化与稳定标识 | 中：影响生成质量与改版鲁棒性 | MVP 用 id/text/index；语义 label 可选 | 同上 |
| 页面发现与遍历 | 高：若做全自动则复杂 | 一期不做全自动探索，用 deeplink+人工列表 | **降低**：按源码得出的清单逐页解析即可 |
| 与 MCP 集成方式 | 中：影响使用体验 | 固定为「schema + 1 个 get_capabilities」 | 同上 |
| 测试与回归 | 中：影响可持续使用 | 提供重生成 + 简单 diff/校验即可 | 仅测这一款 App，范围小 |

## 4. 总结

- **范围**：**一期仅在你拥有源码的这一个 App 上跑通**即可；有源码时可从静态分析得到 Activity/deeplink 清单，页面发现与遍历难度和工期都会下降。
- **工期**：  
  - **一期（自有源码单 App）**：约 **1.5～2.5 人月**（40～58 人天）；若再收窄到「单页解析 + 源码扫出的清单 + schema + Agent 可读」，可压到约 **1.5～2 人月**。  
  - 完整实现「多 App、无源码」的 CLI-Anything 式能力：约 **2.5～4.5 人月**；MVP（单页解析 + 契约驱动 + 单 App schema + Agent 可读）约 **1～1.5 人月**。
- **难点**：**(1) 输入无源码、只能靠 UI 树与契约**——**一期有源码则弱化**；(2) **页面发现与遍历**——**一期有源码则改为按清单逐页解析即可**；(3) 页面 ID 与元素标识的稳定性；(4) 与 MCP 的集成方式；(5) 测试/回归。优先在自有源码单 App 上跑通，可显著降低风险与工期。
