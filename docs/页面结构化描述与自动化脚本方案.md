# 页面结构化描述与自动化脚本方案

> 面向「自己 App + 固定 schema/路径 + Agent 生成并自愈脚本」的说明与设计要点。

---

## 1. 页面/屏幕的「结构化描述」详细说明

### 1.1 概念

**页面/屏幕的结构化描述** 指：用机器可读的方式表达「当前是哪个页面」以及「当前页面上有哪些可被 Agent 或脚本执行的操作」，便于发现能力、做分支判断和生成/修复自动化脚本。

核心两要素：

- **页面 ID（或屏幕 ID）**：唯一标识「当前界面」的稳定符号，用于匹配、分支和去重。
- **可执行操作列表**：当前页面可见、可用的原子动作（点击、输入、滑动、通过 deeplink 跳转等），每条带参数与语义，供 Agent 选择或写入脚本。

### 1.2 页面 ID 的几种形态

| 形态 | 说明 | 与 phone_pilot 的对应 |
|------|------|------------------------|
| **Activity / 界面类名** | Android 的 `Activity` 名、Harmony 的 Ability 等 | `phone_get_page_state` 已返回 `activity`，可直接或规范化后作页面 ID |
| **Deeplink / Schema** | 如 `myapp://home`、`myapp://detail?id=1` | 打开某 deeplink 后，该 URI 或 path 可作为「目标页面 ID」；与 `phone_open_deeplink` 对应 |
| **语义化 ID（自建）** | 如 `home`、`detail`、`settings`，由你们在配置或脚本里维护「Activity/URI → 语义 ID」映射 | 便于分支和子流程命名，不依赖系统实现细节 |
| **UI 签名 / 指纹** | 基于当前 UI 树或关键元素生成的短哈希/签名 | 可与 `ui_signature`、`phone_get_page_state` 的 elements 结合，用于「是否还是同一页」的判定 |

实际可组合使用：例如「语义 ID + Activity 兜底」——优先用 `home`/`detail`，若未配置则用 `activity`。

### 1.3 可执行操作列表（单页维度）

对**当前这一屏**，列出「能执行的动作」及调用方式，例如：

- **操作类型**：`tap`（点击）、`type`（输入）、`scroll`（滑动）、`navigate`（跳转，如 deeplink）、`long_press`、`swipe` 等。
- **目标**：  
  - 点击/长按：用 `phone_get_page_state` 的 **元素 index** 或 **text/id** 定位（与 `phone_tap_element(index)` 一致）。  
  - 跳转：用 deeplink URI（与 `phone_open_deeplink(uri)` 一致）。
- **参数**：如 `type` 的文本、`scroll` 的方向、deeplink 的 query 等。
- **可选语义**：如「提交」「返回」「去设置」，便于 Agent 按意图选操作。

示例（与现有 MCP 对齐）：

```json
{
  "page_id": "detail",
  "activity": "com.example.app/.DetailActivity",
  "operations": [
    { "id": "op_1", "type": "tap", "target": "index", "value": 3, "label": "提交" },
    { "id": "op_2", "type": "tap", "target": "index", "value": 1, "label": "返回" },
    { "id": "op_3", "type": "navigate", "target": "deeplink", "value": "myapp://list?tab=2", "label": "去列表 Tab2" }
  ]
}
```

这样 Agent 或脚本引擎可以：

- **发现**：当前页是 `detail`，能做「提交」「返回」「去列表 Tab2」。
- **分支**：若目标为「去列表」，选 `op_3`；若为「提交」，选 `op_1`。
- **生成脚本**：把选中的操作转成 `phone_tap_element(3)`、`phone_open_deeplink("myapp://list?tab=2")` 等 MCP 调用。

### 1.4 和 phone_pilot 现有能力的对应

| 能力 | 在「页面结构化描述」中的角色 |
|------|------------------------------|
| `phone_get_page_state(device_serial, annotate_elements=True)` | 提供「当前 activity + 元素列表（index/文本/bounds）」和可选标注图，是**构建「可执行操作列表」的输入**；元素 index 即 tap 的 target。 |
| `phone_tap_element(device_serial, index)` | 执行「可执行操作列表」中 `type=tap, target=index` 的项。 |
| `phone_open_deeplink(device_serial, uri)` | 执行「可执行操作列表」中 `type=navigate, target=deeplink` 的项；uri 也可作为**目标页面 ID**（到达后的页面）。 |
| `phone_find_element` / `phone_ocr_find` 等 | 用于在「当前页」找不到预期元素时做重试或自愈（例如弹窗、加载中），或用于生成「按文本/OCR 查找再点击」的脚本步骤。 |

因此：**页面结构化描述 = 对 `phone_get_page_state` 结果 + 你们约定的页面 ID / deeplink 的进一步抽象和规范化**，便于做分支、子流程和脚本生成/修复。

### 1.5 小结

- **页面 ID**：来自 activity、deeplink 或自建语义 ID，用于「当前在哪一屏」的识别与分支。
- **可执行操作列表**：来自当前 UI 树（元素 index/文本）+ 已知 deeplink，每条对应一类 MCP 可执行动作（tap/type/navigate/…）。
- 二者结合即「页面/屏幕的结构化描述」；Agent 据此发现能力、选分支、生成并修改自动化脚本。

## 2. 带分支与子流程、Agent 运行时自动识别

### 2.1 需求要点

- 流程需要**带分支**（例如：若当前是页面 A 做 X，否则做 Y）。
- 可能产生**子流程**（如「登录」「进入设置」），可被多条主流程复用。
- 希望 **Agent 在运行时能自动识别** 当前处于哪条分支、是否需要进入子流程。

### 2.2 实现思路（与结构化描述结合）

- **分支条件**：以「当前页面 ID」为主键。  
  - 例如：`if page_id == "login" then 执行登录子流程`；`elif page_id == "detail" then 点击提交`。  
  - 页面 ID 可由 `phone_get_page_state` 的 activity 或 deeplink 到达后的约定 ID 提供。
- **子流程**：  
  - 把「登录」「进入设置」等封装成**命名的子流程**（一组步骤或一段脚本）。  
  - 主流程中用「进入子流程(登录)」「进入子流程(进入设置)」这样的节点引用；Agent 或脚本引擎在运行时根据当前页面 ID 和任务目标决定是否进入子流程。
- **Agent 自动识别**：  
  - 每步执行后（或步骤前）调用 `phone_get_page_state` 得到当前 activity/元素列表。  
  - 用「页面 ID + 可执行操作列表」与预定义的**流程/分支表**或**脚本结构**做匹配：  
    - 若匹配到某分支或子流程入口，则自动进入该分支或子流程；  
    - 若匹配不到（异常页、弹窗、新版本 UI），可走「重试 + 自愈」或「调 MCP 验证路径后改脚本」（见下节）。

这样即可在**不改变「页面 ID + 可执行操作列表」**这一抽象的前提下，支持带分支和子流程，并由 Agent 在运行时根据当前状态自动识别走哪条路径。

## 3. 完整工作流：需求 → 生成脚本 → 执行 → 出错自愈并改脚本

### 3.1 目标（你的要求归纳）

1. **A 阶段（当前目标）**：覆盖「自己 App」内所有需要自动化的页面/流程；后续再扩展到 B（其他 App）。
2. **自然语言驱动**：你对大模型说需求，它根据**现有 schema（deeplink 等）和/或手动点击跳转**，在判断执行完毕后，**生成一份自动化脚本**。
3. **执行与自愈**：你再说「执行这个脚本」，Agent 按脚本执行；若执行过程中**出现错误**，Agent **再次借助 MCP 工具验证路径**（例如 `phone_get_page_state`、`phone_find_element`、重试等），然后**自动修改脚本**，覆盖更多场景（如多一种分支、多一步弹窗关闭），便于下次执行更稳。

### 3.2 流程拆解

```
┌─────────────────────────────────────────────────────────────────────────┐
│ 1. 需求输入                                                              │
│    用户用自然语言描述目标（如「每次打开 App 后进入详情页并提交表单」）       │
└─────────────────────────────────────────────────────────────────────────┘
                                      │
                                      ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ 2. 探索与生成脚本                                                        │
│    • Agent 使用 MCP：phone_get_page_state、phone_tap_element、           │
│      phone_open_deeplink、phone_find_element 等                           │
│    • 结合已有 schema（deeplink）/ 或通过「手动点击」一步步导航              │
│    • 判断「执行完毕」后，生成一份自动化脚本（如 Python script_api 或       │
│      结构化步骤序列），并可选保存为「命名脚本」                             │
└─────────────────────────────────────────────────────────────────────────┘
                                      │
                                      ▼
┌─────────────────────────────────────────────────────────────────────────┐
│ 3. 执行脚本                                                              │
│    用户说「执行这个脚本」→ Agent 调用 phone_run_script(path=...) 或       │
│    按步骤依次调用 MCP 工具执行                                            │
└─────────────────────────────────────────────────────────────────────────┘
                                      │
                          ┌───────────┴───────────┐
                          │ 是否出错？             │
                          └───────────┬───────────┘
                               否 │         │ 是
                                  ▼         ▼
                            ┌─────────┐  ┌─────────────────────────────────┐
                            │ 结束    │  │ 4. 自愈与脚本更新                 │
                            └─────────┘  │ • 用 MCP 重新验证：get_page_state│
                                         │   find_element、重试、截图等      │
                                         │ • 分析失败原因（错误页/弹窗/缺失   │
                                         │   元素/版本差异等）                │
                                         │ • 自动修改脚本：增加分支、步骤、   │
                                         │   弹窗处理或备用路径，覆盖更多场景 │
                                         │ • 可选：把新路径写入「经验库」或   │
                                         │   更新「页面 ID + 操作列表」       │
                                         └─────────────────────────────────┘
                                                          │
                                                          ▼
                                         ┌─────────────────────────────────┐
                                         │ 5. 再次执行（或保存后下次执行）    │
                                         └─────────────────────────────────┘
```

### 3.3 与现有能力的对应

- **探索与生成**：MCP 已有 `phone_get_page_state`、`phone_tap_element`、`phone_open_deeplink` 等；缺少的是「把一次探索过程固化为脚本」的约定（脚本格式、存储位置、是否带「页面 ID + 操作列表」的元数据）。这部分可由你们约定一种脚本模板或 JSON/YAML 步骤描述，由 Agent 生成并保存。
- **执行**：`phone_run_script(path=...)` 已支持跑 Python 脚本；若脚本是「步骤序列」而非 Python，则需要一层把步骤转成 MCP 调用的执行器（可在 Agent 内实现，或新增一个轻量解释器）。
- **出错后验证**：继续用现有 MCP（get_page_state、find_element、screenshot、重试）做诊断；**自动修改脚本**需要 Agent 具备「读当前脚本 + 编辑并写回」的能力（文件编辑 + 可选与经验库/页面描述的联动）。

## 4. CLI-Anything 与移动端 / Deeplink 验证

### 4.1 CLI-Anything 调研结论（subagent 已输出）

- **是什么**：香港大学 HKUDS 的开源项目 [CLI-Anything](https://github.com/HKUDS/CLI-Anything)，对**有源代码的桌面/服务器软件**执行一条命令，通过 7 阶段流水线**自动生成该软件的生产级 CLI**（基于 Click，带 `--help` / `--json`），供 AI Agent 或脚本调用，**直接调真实应用后端**，避免截图/像素级 GUI 自动化。
- **移动端**：**官方未支持** Android/iOS；**未见**与 Appium、UIAutomator、ADB 或移动端 MCP 的结合案例。其思路（结构化、可发现、可执行）**可迁移**到移动端，但需：
  - 输入从「源码」改为 **UI 树/可访问性树或契约**（页面 + 可操作元素）；
  - 执行从「本地进程」改为 **ADB/Appium/UIAutomator** 等；
  - 增加 **「页面 ID + 可执行操作列表」** 的抽象，并可结合 **deeplink/schema** 做导航。
- **与你们方案的关系**：CLI-Anything 没有「页面」「固定路径」「deeplink」概念；你们在移动端做的「页面结构化描述 + 固定操作路径 + deeplink」可以视为一种**移动端上的类似思想**——用结构化、可发现、可执行的能力替代纯「看图点击」，并可借鉴其「自描述 + 机器可读」的设计（如操作列表带类型、参数、说明）。

### 4.2 是否可以用在移动端？

- **直接使用**：**不能**。CLI-Anything 面向桌面/服务器软件源码，不接移动设备或 UI 树。
- **思路迁移**：**可以**。在你们项目中：
  - 用 `phone_get_page_state` + 约定「页面 ID + 可执行操作列表」实现**移动端的「结构化描述」**；
  - 用 `phone_open_deeplink`、`phone_tap_element` 等作为**可执行操作**；
  - 若将来做「从 UI 树/契约自动生成脚本或 schema」，可参考 CLI-Anything 的「分析 → 设计 → 实现」流水线，把「分析」改为基于 UI 树或已有契约。

### 4.3 在 Demo App 上验证 Deeplink

- 你们打算在**自己的 Demo App** 上验证 deeplink，这与 CLI-Anything 无直接依赖。
- **推荐做法**：
  - 在 Demo App 中实现并注册 **URL scheme / App Link**（如 `myapp://home`、`myapp://detail?id=1`）。
  - 使用 phone_pilot 的 **`phone_open_deeplink(device_serial, uri="myapp://...")`** 在真机/模拟器上验证能否正确拉起并进入对应页面。
  - 将验证过的 URI 纳入「页面 ID + 可执行操作列表」中的 **navigate** 类操作，或作为**目标页面 ID** 的来源，供 Agent 生成脚本和分支时使用。

完整技术细节见：`docs/CLI-Anything技术调研报告.md`。

## 5. 文档与后续可落地的点

- **页面结构化描述**：可在项目中新增一份「页面 ID + 可执行操作列表」的 **schema 定义**（JSON Schema 或 TypeScript 类型），并约定由 `phone_get_page_state` 的结果 + 配置/映射 生成或补全该描述。
- **带分支/子流程的脚本格式**：定义一种最小可用的「步骤 + 分支 + 子流程引用」格式（或直接用 Python script_api 的链式调用 + 条件分支），供 Agent 生成与修改。
- **自愈后写回脚本**：约定脚本存放位置（如 `workflows/` 或 `.recordings/scripts/`）和版本/命名规则，便于 Agent 读入 → 修改 → 写回并再次执行。
- **Deeplink 验证**：在 Demo App 中实现 scheme，用 `phone_open_deeplink` 做回归验证，并把 URI 列入「可执行操作」与页面 ID 的配置中。
