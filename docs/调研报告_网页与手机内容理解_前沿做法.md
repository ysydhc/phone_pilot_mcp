# 大模型理解「网页+手机」内容：MCP / Agent / 多模态生态前沿调研

> 调研范围：MCP 与 browser/mobile/screen 设计、多模态模型 UI 理解、Agent 框架实践、2024–2025 新趋势，以及社区共识与前沿方向。

---

## 1. MCP 中与 browser / mobile / screen 相关的 Server 与 Tool 设计

### 1.1 状态暴露方式概览

| 方式 | 特点 | 典型用途 | 代表实现 |
|------|------|----------|----------|
| **Accessibility Snapshot (a11y tree)** | 结构化、语义化；约 50–200 tokens/页；不依赖像素 | 网页自动化、可访问性测试 | Playwright MCP、Puppeteer `accessibility.snapshot()` |
| **Screenshot** | 像素级；约 1,200–5,000 tokens/图；视觉完整 | 视觉验证、布局/外观理解 | Chrome DevTools MCP、纯视觉 Agent |
| **DOM / HTML** | 原始结构；需解析；易受实现细节影响 | 调试、爬虫、部分自动化 | Chrome DevTools MCP |
| **结构化元素 + ID** | 截图 + 元素 ID 映射，便于“看+点”闭环 | 高精度点击/填表 | Chrome DevTools MCP（snapshot 带 ID） |

### 1.2 主要 MCP Server 与设计要点

- **Playwright MCP（微软官方）**
  - **核心**：用 **accessibility snapshot** 代替截图，把页面表示为角色(role)、名称(name)、状态(state) 等结构化文本。
  - **优势**：2–5KB 级 snapshot vs 100KB+ 截图，token 少、确定性高、对 UI 变化更稳；与 LLM 文本输入天然契合。
  - **能力**：导航、点击、填表、等待动态元素；适合任务自动化、测试生成、数据抽取。
  - 参考：Playwright Agents 文档、Cursor Directory 的 Playwright MCP。

- **Chrome DevTools MCP（Chrome 官方）**
  - **能力**：控制真实 Chrome、截图、DOM/CSS 检查、网络/控制台、性能追踪（Core Web Vitals）。
  - **状态暴露**：截图 + 可带唯一 ID 的页面快照，便于模型做“结构理解 + 元素定位”。
  - **交互**：`click`、`fill_form`、等待元素、调整视口等；常与 Copilot / Cursor / Gemini CLI 等配合做 E2E 测试与 UI 调试。
  - 仓库：`ChromeDevTools/chrome-devtools-mcp`。

- **WebMCP（W3C 社区标准，Chrome 146+ 预览）**
  - **思路**：网站主动向 Agent **暴露结构化工具**（名称、描述、输入/输出 JSON Schema），Agent 直接调用“工具”而非解析 DOM/截图。
  - **API**：`navigator.modelContext.registerTool()`；也可用 HTML 表单 + schema 声明。
  - **效果**：相较截图方案约 **89% token 减少**、结果确定、可复用浏览器登录态；需站点配合实现。
  - 参考：webmcp.link、Chrome 146 WebMCP 文档。

### 1.3 设计共识与取舍

- **共识**：a11y tree / 结构化 snapshot 在“可获取到”的场景下，比纯截图更省 token、更稳、更易被 LLM 推理。
- **争议/取舍**：纯视觉方案不依赖 DOM/a11y，可跨桌面/原生 App/封闭环境；结构化方案依赖网页或可注入的运行时（如浏览器、部分移动容器）。

## 2. 多模态模型对「截图/界面」的理解能力

### 2.1 商业多模态模型（GPT-4V、Claude、Gemini）

- **GPT-4V**：图像编码为 token，强于复杂场景与关系推理、多步调试；需配合定位/ grounding 方法才能精确执行点击等动作。
- **Claude**：在文档、图表、截图、UI 等结构化视觉内容上表现突出，适合从界面中抽取信息、理解布局与控件。
- **Gemini**：原生多模态（文本/图像/音视频），强调多图上下文与实时理解；适合连续屏幕状态分析。

### 2.2 开源多模态模型在 UI 理解上的用法

- **Qwen-VL（Qwen-VL-Plus / Max）**
  - 高分辨率（百万像素级）、多宽高比；OCR 与视觉推理强。
  - 用于 **Agent 化 UI 交互**：理解按钮/布局、多步场景、QA 与自动化；与 GPT-4V/Gemini Ultra 在多项 benchmark 可比。
  - 参考：Qwen 官方博客、typevar.dev 的 Qwen-VL Agent 文章。

- **InternVL2（1B–108B）**
  - 8k 上下文，支持图像/视频/文档等；在文档理解、图表、场景文字、OCR 上接近商业模型。
  - 可用于截图问答、界面理解、文档/图表分析。

- **LLaVA**：常见于通用视觉-语言任务；UI 场景多为“看图问答”，与专门做 GUI grounding 的模型相比更偏通用。

### 2.3 增强“截图→动作”的辅助方法

- **OmniParser（微软）**
  - 问题：GPT-4V 等能“看”截图，但难以精确对应到可操作元素。
  - 做法：检测可交互元素 + 图标/功能语义描述 → 将截图转为**带语义的结构化元素**，再交给 GPT-4V 等做决策。
  - 效果：在 ScreenSpot、Mind2Web、AITW、WindowsAgentArena 等达到 SOTA；也可接 Phi-3.5-V、Llama-3.2-V。
  - 参考：Microsoft Research OmniParser、arXiv 2408.00203。

## 3. Agent 框架中「理解界面」的实践

### 3.1 Cursor + MCP

- **Browser / Playwright 集成**：通过 MCP 使用 Playwright 或 Chrome DevTools MCP，以 **a11y snapshot** 为主、截图为辅，在 Composer/Agent 中完成表单、抽取、测试等。
- **配置**：Cursor 设置 → MCP → 添加 server（如 `npx -y @playwright/mcp@latest`），工具仅在 Composer Agent 中可用。
- **特点**：强调“结构化 > 像素”，与 Playwright 官方推荐的 Agent 方案一致。

### 3.2 Adept

- **定位**：以“看懂屏幕 + 执行操作”为核心的 Agent，面向企业工作流自动化。
- **模型线**：ACT-1（浏览器与数字工具）→ ACT-2（Fuyu 系，像素输入 + 坐标/按键输出）→ **Fuyu-Heavy**（多模态，UI 理解与推理强，与 GPT-4V/Gemini Ultra 同档）。
- **能力**：Locate（UI 元素）、Web VQA、多步规划与执行；用于供应链、财务文档、CRM、数据抽取等。
  - 参考：adept.ai 博客、the-decoder 对 Fuyu-Heavy 的报道。

### 3.3 其他产品与工具

- **Chrome DevTools MCP**：与 VS Code / Cursor / Gemini CLI 等集成，用于自动化测试、性能审计、UI 问题排查。
- **MobAI、agent-device、LlamaTouch**：移动端（iOS/Android）提供截图、UI 树、OCR、DSL 或 tap/swipe/type 等，供 Agent 控制真机或模拟器。

## 4. 2024–2025 新趋势

### 4.1 端到端 UI 理解模型

- **ScreenAI（Google）**
  - 5B 参数视觉-语言模型，专注 **UI + 信息图**；基于 PaLI + pix2struct 式灵活切块，保持宽高比。
  - 核心任务：**屏幕标注**（元素类型、位置、描述）→ 用 LLM 自动生成 QA、导航、摘要等数据。
  - 在 WebSRC、MoTIF、Multi-page DocVQA、Widget Captioning 等 SOTA；ChartQA、DocVQA、InfographicVQA 同规模最佳。
  - 发布数据集：Screen Annotation、ScreenQA Short、Complex ScreenQA。
  - 参考：Google Research Blog、IJCAI 2024、arXiv 2402.04615。

### 4.2 多模态 + 可执行动作（click、type）的闭环

- **ShowUI（CVPR 2025）**
  - **Vision-Language-Action**：从截图直接输出可执行动作（如 click 类型 + 位置）。
  - 创新点：UI 引导的视觉 token 选择（减约 33% 冗余 token）、视觉-语言-动作交织流式、小规模高质量 GUI 指令数据。
  - 约 2B 参数、256K 样本；零样本截图 grounding 约 75.1%；支持 Web/移动/桌面；开源（showlab/ShowUI）。
  - 参考：arXiv 2411.17465、NeurIPS 2024 / CVPR 2025。

- **WinClick、Aria-UI 等**
  - **纯视觉 grounding**：不依赖 HTML/DOM/AXTree，适合 Windows 桌面与跨平台；通过预测截图上的归一化坐标 [x,y] 执行 click/type。
  - Aria-UI 引入动作历史，做上下文感知的连续操作。

- **ActionEngine**
  - 从“反应式”到“可编程”：Crawling Agent 建 GUI 状态机记忆，Execution Agent 生成可执行 Python；在 WebArena Reddit 任务上约 95% 成功，单次 LLM 成本约降 11.8×。

### 4.3 移动端与设备侧

- **Ferret-UI Lite（Apple）**
  - 约 3B 参数 **端侧**模型：看屏幕图 + 理解 UI 元素；ScreenSpot-V2 grounding 约 91.6%，AndroidWorld 约 28%。
  - 说明移动端“设备上理解界面”成为明确方向。

- **AndroidWorld / 多智能体**
  - 多 Agent（规划、编排、上下文、执行、屏幕分析等）在 AndroidWorld 上可达 100% 成功率；针对上下文污染、输入失败、循环动作等问题做专门设计。
  - 参考：arXiv 2602.07787。

### 4.4 评估与 Benchmark

- **Mind2Web / Mind2Web 2**：长程、真实感网页任务；Mind2Web 2 用 Agent-as-a-Judge 评估正确性与归因（NeurIPS 2025）。
- **Mind2Web-Live**：实时网站下的自主 Web Agent，104 任务，Playwright/Selenium 步骤与多层标注。
- **ScreenSpot / ScreenSpot-V2 / ScreenSpot-Pro**：GUI 元素定位与 grounding。
- **AITW、WindowsAgentArena**：跨应用/桌面 GUI 任务。
- **FineState-Bench**：细粒度状态控制，现有系统约 32.8%，说明“粗粒度任务完成”与“细粒度交互”之间仍有差距。
- **OSWorld、AndroidWorld**：端到端系统级 GUI 与移动端任务。

## 5. 总结：社区共识、争议与最前沿 2–3 个方向

### 5.1 社区共识

- **结构化优先**：在浏览器/可注入环境，a11y tree 或等价 snapshot 比纯截图更省 token、更稳、更易被 LLM 利用；Playwright MCP、WebMCP 都体现这一点。
- **网站主动暴露**：WebMCP 代表“站点声明工具 + Schema”的路线，与“Agent 爬 DOM/截图”形成对比，被寄望为长期标准。
- **纯视觉路线**：在无 DOM/a11y 的场景（桌面 App、封闭移动 App、跨平台），纯视觉 + 坐标 grounding 是主流，且 2024–2025 模型（ShowUI、WinClick、OmniParser 增强）明显加强。
- **多模态 + 动作**：从“看图说话”到“看图并输出 click/type”的 VLA 或 VLM+grounding 成为标配方向；benchmark（Mind2Web、ScreenSpot、AITW、OSWorld）围绕任务成功率与 grounding 精度展开。

### 5.2 争议与取舍

- **结构化 vs 纯视觉**：结构化依赖环境（Web/可注入）；纯视觉通用但 token 与精度成本高；混合方案（如 OmniParser + GPT-4V）在部分 benchmark 领先。
- **端侧 vs 云侧**：Ferret-UI Lite 等端侧模型强调时延与隐私；复杂规划与多步仍多依赖云侧大模型。
- **单 Agent vs 多 Agent**：AndroidWorld 等表明多 Agent 分工可显著提升成功率，但系统复杂度和工程成本更高。

### 5.3 最前沿的 2–3 个方向（判断）

1. **WebMCP + 站点声明式工具**
   - 浏览器与 W3C 将“网站作为工具提供方”标准化，Agent 直接调工具而非解析 DOM/截图，实现大幅省 token 与稳定契约；若普及，会改变“网页理解”的形态（从“理解界面”到“调用声明好的能力”）。
   - 当前处于 Chrome 146 预览与社区推广期，生态依赖站点适配。

2. **Vision-Language-Action 端到端模型（如 ShowUI）与纯视觉 grounding**
   - 一条龙：截图 → 理解 → 输出可执行动作（click/type 等），不依赖 HTML/DOM/AXTree，跨 Web/桌面/移动。
   - 与 OmniParser 等“增强现有 VLM”的路线并存；小参数（2B 级）VLA 模型 + 高质量 GUI 数据是当前热点。
   - 前沿在于：更好利用 UI 图结构（token 选择、图结构）、多轮与历史动作的建模（如 Aria-UI）、以及与小模型/端侧结合（Ferret-UI Lite）。

3. **多模态 + 状态机/可编程执行（ActionEngine 式）与多 Agent 分工**
   - 不只“看一帧→动一下”，而是 Crawling Agent 建状态/记忆，Execution Agent 生成可执行脚本或程序，减少反复调用 VLM、提高成功率和成本效率。
   - 与“多 Agent 分工”（规划、屏幕分析、执行、纠错）结合，在 AndroidWorld、Mind2Web 等长程任务上成为提升上限的主要手段；争议在于复杂度和可维护性。
